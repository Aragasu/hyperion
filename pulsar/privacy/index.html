Privacy
policy.

Pulsar keeps the identifiers and settings it needs to run your server. It is not an advertising platform, it does not sell data, and it does not keep a general archive of your chat.

Effective 20 October 2026 Version 1.0 No sale. No ads.
What this means

Enough data to run the bot, and no more than that.

  • IDs and settings are stored so commands, tickets and moderation work.
  • Message text is read to answer commands and run filters. It is only written down by features that need it.
  • The dashboard stores your Yapper profile and a hashed session. It never stores your Yapper access token.
  • Data lives in JSON files on the machine running Pulsar — not in a central analytics service.

Removing the bot stops future processing, but it does not automatically erase records. Ask for deletion here.

01

Scope

This policy covers the Pulsar bot, this website, the server dashboard, and the command and embed builders. It explains what the operator of this Pulsar instance processes, why, and what you can do about it.

It does not cover Yapper, Hyperion’s other services, Google Fonts, or a media detector that a server chooses to configure. Those are separate services with their own policies. This Pulsar instance is operated for Hyperion; “we” and “us” mean that operator. Pulsar is a hosted service — there is no self-hosted copy for this policy to describe.

02

The short version

Pulsar is a bot, so it has to see the messages in channels it can read in order to answer commands and run the features a server has switched on. Most of that happens in memory and leaves no record.

What does get written down falls into three groups: identifiers and settings needed to run your server, records the features are for (warnings, tickets, levels, custom commands and the like), and your dashboard session. There is no advertising profile, no sold data, and no payment information because Pulsar has no paid plans.

The one thing worth repeating

Data is stored as plain JSON on the machine that runs Pulsar. Anyone with access to that machine, its data directory, or its backups can read it. Pulsar does not encrypt it at rest.

03

What Pulsar processes

Not every server uses every feature, so not every row below applies to every server. A feature that is switched off does not write its records.

WhatWhy
Yapper IDs User, server, channel, role and message IDs are used to know who asked, where to reply, who may run a command, and which settings apply.
Settings Modules, automod rules, welcome messages, log channels, ticket panels, raid settings and the rest are stored per server so they survive a restart.
Records the features exist for Warnings, cases, temp roles and bans, tickets, giveaways, polls, trivia scores, counting, levels, coins, game state, reminders, tags, sticky notices, schedules and price watches.
Content you save Custom command scripts and responses, embed copy, welcome and leave text, ticket subjects, AFK reasons and scheduled messages are stored so the bot can use them later.
Dashboard session Your public Yapper profile, a hashed session ID, a CSRF value, the server you last opened, timestamps and the changes you made. See section 5.
Message text and attachments Read while handling a message, to find commands and run the filters a server enabled. Mostly not stored. See section 4 for the exceptions.
Technical logs The process writes operational errors and identifiers to its log. These are for running the bot; they are not a chat archive.

Do not put health, political, religious, sexual or other sensitive information into a field Pulsar stores. The bot does not ask for it, and server staff may be able to read the fields it does store.

04

Messages and attachments

Pulsar receives messages from channels it is allowed to read. It uses the text to decide whether a message is a command, whether it trips an automod or link rule, whether it earns XP, whether it continues a game, and whether it is a number in a counting channel. A message that does none of those things is normally dropped after processing.

There is no general chat log. The exceptions are specific features that exist to keep something:

  • Honeypot. The most recent 20 catches per server are written to data/honeypot.json, with the user ID, username, up to 200 characters of the message, the time, the action taken and whether it succeeded. That record is the point of the feature: staff need to see what was posted.
  • Automod. Recent message text is kept in memory, per channel and author, so repeated or near-identical messages can be recognised. It is not written to disk and disappears when the process restarts. An alert posted to a channel may quote the flagged message; that alert is a normal Yapper message and Yapper stores it.
  • Media scanning. If a server configures a detector, Pulsar sends that endpoint the attachment URL, the file kind and the file name. It does not upload the file’s bytes itself. The detector may return a verdict and any text it read from the image; a matching alert may quote that text. The detector belongs to whoever the server pointed it at.
  • Tickets. Pulsar stores the ticket’s subject, opener, participants, channel ID, status and timestamps. The conversation itself stays in the private Yapper channel; Pulsar does not make a separate transcript.
  • Sticky notices, custom commands, embeds, schedules and reminders. The text you ask Pulsar to keep is stored so it can post or run it later.

Attachments and links are also inspected from their names and URLs for the file checks. Those checks do not download the file.

05

The dashboard and signing in

The dashboard uses Yapper sign-in with the identify scope. Yapper tells us who you are; it does not give us your password, and the scope does not include your email or your messages.

The access token Yapper returns is used once, during sign-in, to ask who you are. It is then dropped and never written to disk. There are no refresh tokens in this flow.

What the session store keeps is your Yapper user ID, username, display name and avatar URL, a random session ID stored only as a SHA-256 hash, a CSRF value the page needs in order to submit forms, the server you last selected, and the times the session was created, last used and expires. The session ID itself is carried only in an HttpOnly cookie in your browser; the server keeps the hash, not the ID.

Sessions last 30 days by default. The operator can configure a different lifetime; either way, signing out ends the current browser’s session immediately, and p!dashboard revoke in chat ends every dashboard session on your Yapper account.

Each server’s dashboard also keeps an audit log of the most recent 400 changes, with the old and new values, the person who made the change and the time. The server owner can read it in the dashboard and with p!dashboardlog. It is there so a bad change can be understood and undone.

06

What Pulsar does not collect

  • Your Yapper password. Sign-in happens on Yapper; Pulsar never sees it.
  • Your email address, through the dashboard. The identify scope does not provide it.
  • Payment or billing information. Pulsar has no paid plans, subscriptions or purchases.
  • Advertising identifiers, cross-site trackers or analytics profiles. The public site has no analytics script.
  • Your precise location, contacts, microphone or camera. The dashboard sends a permissions policy that turns those off.
  • A general archive of your messages. The feature-specific exceptions are listed above.

Pulsar does not sell, rent or trade data. It does not use your content to train AI models, and it does not send your data to an AI provider.

The public site loads typefaces from Google Fonts. That request is made by your browser to Google, not by Pulsar, and it carries ordinary request information such as your IP address and browser user agent. If you want to avoid it, a content blocker or a local font fallback will stop the request; the page still works.

07

Where the data lives

The bot writes JSON files under its data/ directory on the machine that runs it. There is no central Pulsar database, no hosted analytics service and no third-party data warehouse. The website is static.

The files are readable by the operator and by anyone who has access to the host, its storage volume or a backup. Server owners can see parts of them through the bot and dashboard: their settings, warnings, cases, tickets, custom commands, honeypot catches and audit log.

If the operator takes backups of the machine or the data directory, those copies follow the backup’s own retention. Deleting a record from the live files does not necessarily delete it from an older backup.

08

How long it is kept

There is no single retention period, because different features keep different things. These are the limits built into the bot:

Dashboard sign-in state10 minutes, in a short-lived cookie during the OAuth round trip.
Dashboard audit logThe most recent 400 actions per server. Older entries fall off.

Warnings, cases, tickets, levels, coins, custom commands, schedules and other saved settingsUntil the server owner or the operator deletes them. There is no automatic expiry.

BackupsWhatever the operator’s backup schedule keeps.

Removing Pulsar does not automatically erase its data. There is no delete-on-leave hook. Removal stops future processing, but the JSON files stay until somebody removes the records. Ask us if you want them gone.

09

Who can see it

  • The operator and the host. Anyone who can read the machine, the data directory or a backup can read the JSON files.
  • Server owners and staff. They can see the settings and records their own server creates, through commands and the dashboard — including warnings, cases, ticket details, custom commands, honeypot catches, automod settings and the audit log.
  • Yapper. Messages Pulsar posts, and the profile returned during Yapper sign-in, are handled by Yapper under its own privacy policy. Yapper also stores the messages in a ticket channel, like any other channel.
  • Google Fonts. Your browser requests the typefaces from Google, which receives ordinary request metadata such as your IP address and user agent.
  • A media detector, if a server configures one. It receives the attachment URL, file kind and file name for the files that server asked to scan. Its operator’s policy applies.

We do not sell or rent data. We may disclose records if the law requires it, or if it is necessary to investigate abuse or protect someone from harm.

10

Security

The dashboard is built to keep its own credentials small: session IDs are random and stored only as hashes, cookies are HttpOnly, mutations need a CSRF value and a same-origin request, and server ownership is checked on every server-scoped request. The Yapper access token is not kept.

None of that encrypts the data files. They are plain JSON. If the host is compromised, or somebody is given access to the data directory, they can read it. Protect the machine, restrict who can reach the dashboard, and treat backups with the same care as the live files.

No service can promise perfect security. If you find a vulnerability, report it privately through Hyperion and do not test it against a server you do not own. Do not put passwords, API keys or bot tokens into custom commands, embeds or any other field Pulsar stores.

11

Your choices

You can ask us to show you, correct or delete records about you. Raise the request in Hyperion and include the Yapper user ID and, where relevant, the server ID. We will try to respond within a reasonable time.

A few practical limits:

  • Access and export. The data is already in JSON files, and server owners can see much of it through the dashboard. We can tell you what is held about a user or server.
  • Correction. Most settings can be changed in the dashboard or with a command. For records such as warnings or ticket subjects, ask the server’s staff or us.
  • Deletion. We can remove specific records from the live data files. We cannot guarantee deletion from older backups or from the operator’s process logs, and we cannot delete Yapper messages that Yapper itself holds.
  • Leaving. Removing Pulsar from a server stops future processing. It does not, by itself, purge the files.

If you are a server owner, you can also clear the settings you control and ask us to remove the server’s records. If you are not the owner, ask the server’s staff first: they may be able to resolve it without involving us.

12

Children

Pulsar is not directed at children. You must be old enough to use Yapper under its terms and to agree to these terms under the law where you live.

If you believe a child’s information has been stored by Pulsar, contact us through Hyperion. We will remove it where we can.

Changes to this policy

We may update this policy as Pulsar changes. The date at the top will change, and the new version applies from that date. If a change is material, we will try to say so in Hyperion or on this page.

If you keep using Pulsar after the date changes, the updated policy applies. If you do not accept it, remove the bot and stop using the service.
